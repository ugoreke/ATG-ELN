# Moving lines into notebooks (after Benchling is confirmed)

Reference for the `eln-transfer` skill ([SKILL.md](SKILL.md)): read it before step 1 of a transfer and follow it at step 9.

The rule: a line is moved, not copied, and not edited. It must never be lost and never appear twice, even if the session stops half-way.

The batch is built and checked with `tools/transfer/transfer.mjs`, never by hand. The tool does not talk to the database: you read the documents with the data tool, the tool works on the saved files, and you send the batch it wrote back through the data tool. Its commands and flags are at the top of that file; its tests are `tests/transfer-tool.test.mjs`. Each rule below is still the rule; "(the tool does this)" and "(the tool refuses this)" say where the tool now enforces it. Never write a batch yourself, and never edit a file the tool wrote.

## Files

- Read documents with the data tool's `out_dir` set to a folder for this run in `scratch/` (for example `scratch/<YYMMDD>_transfer/read-1/`). Each document is saved as `<folder>/<collection>/<id>.json`, and the tool tells from that path which document a file is: do not rename or move the files. Note each document's `version` from the read; the tool takes it as a flag.
- The first read of a run is the copy that step 3 of the transfer asks for. Keep it unchanged. Every later read goes into a new folder (`read-2/`, `after-1/`…) and every plan into a new folder (`plan-1/`…). The tool refuses to write over a file it read or over an earlier plan.
- What else the run folder holds (the manifest, the photos, the page text of each Benchling entry, the reports of the `transfer-verifier` agent) and how a stopped transfer is picked up is in [run-folder.md](run-folder.md). Only lines that agent passed are moved (step 8 of [SKILL.md](SKILL.md)).

## The rules

- **Match the notebook by name.** The notebook's `title` must equal the Benchling entry's name. If no notebook has that name, create one: a new document in `entries` with a new UUID as its id and `{ title, createdAt, updatedAt, protocols: [], blocks: [], benchlingUrl }`. The tool builds it in the same batch as the move when you give `--new-notebook <new UUID> --title <Benchling name>` instead of `--notebook` (make the UUID with `node -p "crypto.randomUUID()"`). If a notebook clearly is that entry under an older or shorter name, rename it to the Benchling name instead of creating a second one, and say so in the report: add `--title <Benchling name>` to the plan for that notebook, and the rename goes into the same pinned batch. Which notebook is the right one is your judgment; the tool only warns when the notebook already points at another Benchling entry. A notebook is created once: if a batch that creates one was refused or was not applied all at once, read `entries/<that id>` before planning again, and if it is there, plan against it with `--notebook` (the tool refuses to create a notebook that was read or that `moved` already names; the data tool refuses a write without a pin over a document that exists).
- **One batch per notebook, both documents pinned.** Plan it:

  `node tools/transfer/transfer.mjs plan --daily <read>/logs/daily.json --daily-version <n> --notebook <read>/entries/<notebook id>.json --notebook-version <n> --benchling-url <entry URL> --out <run>/plan-<k> <line id> <line id> …`

  It writes `batch.json`, the two documents the batch points to, and `lines.json` (the moved lines exactly as stored: the saved copies for the check afterwards). What the batch holds, in a single database batch write, with each document pinned to the version you read (the tool does this):
  1. the notebook, written first: `blocks` = its current blocks plus the moved lines, sorted by `at`; `benchlingUrl` and `updatedAt` set. Each moved line is copied exactly as it is in Daily (every field as stored: `id`, `at`, `text`, `caption`, `transcript`, `assetId`, `url`, and for a voice memo also `chunks`, `sha256`, `bytes`, `mime`, `fileName`, `duration`, `attachedAt`, `transcribedAt`, `transcriber`, `audioRemovedAt`). Any line whose `id` is already in the notebook is skipped there and still taken out of Daily.
  2. `logs/daily`: `blocks` = its current blocks minus the moved lines; each moved id added to `moved` as `"<line id>": { "to": "<notebook id>", "at": "<now, ISO>" }`; `updatedAt` set.

  Send it with the data tool's `batch` action, passing the `writes` list from `batch.json` exactly as written (each entry names its file in `file_path` and its pin in `if_version`; a notebook that is being created has no pin). If the batch is refused because a document changed, re-read both documents into a new folder and plan again, into a new folder, from what is there now; never retry with old contents, and never change an `if_version`. Repeat for the next notebook.

  If the plan says there is nothing to do (`nothingToDo`), the lines are already moved; send nothing.
- **What is never moved** (the tool refuses each of these, with the reason): a line id that is not in Daily; a line that `moved` says went to another notebook; a voice memo without a transcript, which stays in Daily; a target that is a meeting or a page of a tab the user added; a source other than `logs/daily` or a target outside `entries`; a notebook that would grow past 230,000 bytes (a stored document may be 256 KiB). A refusal means nothing was written: read the message, do not work around it.
- **If the batch result says it was not applied all at once,** check the notebook first. A line is done only when it is in the notebook; only then may it be absent from Daily. Re-read both documents and run `verify` (next rule): a line reported as `still-in-daily` or `not-moved` did not finish, so plan the move again from the new read; the tool then skips what is already in the notebook.
- **Check afterwards.** Wait about ten seconds, re-read the notebook and `logs/daily` into a new folder, and run:

  `node tools/transfer/transfer.mjs verify --daily <after>/logs/daily.json --notebook <after>/entries/<notebook id>.json --notebook-version <n> --copies <run>/plan-<k>/lines.json --out <run>/check-<k>`

  It confirms every moved id is in the notebook exactly once, field for field equal to its saved copy, and not in Daily's `blocks`. If a line is missing from the notebook (a device saved an older copy over it), add it back from your saved copy with another pinned write: the tool writes that write as `<out>/repair/batch.json`; send it as it is, then re-read and verify again until it is clean. If a moved line is back in Daily's `blocks`, leave it: the app hides and removes it by itself because its id is in `moved` (the tool reports such a line as fine). The repair only adds lines. A line reported as `changed` (someone edited it in the notebook after the move) or `duplicate` is never overwritten or removed by the tool: tell the user. A line reported as `lost` has no saved copy anywhere; restore it from the Benchling entry as described in the next rule.
- **Check the last transfer too.** At the start of every transfer, before moving anything new, go through `moved` in `logs/daily`: every id listed there must be in the notebook named by its `to`. A device that was offline can save an older copy of a notebook hours later and drop a moved line. Run the audit on the first read of the run, pointing `--copies` at the folders of earlier runs in `scratch/` (it may be given more than once):

  `node tools/transfer/transfer.mjs audit --dir <read> --copies scratch/<earlier run> --out <run>/audit`

  It lists every such line under "moved lines missing from their notebook", with the saved files that hold a copy. If one is missing, put it back from the copy saved in `scratch/` (or from the Benchling entry if no copy exists) with a pinned write, and tell the user: run `verify` for that notebook with `--copies <the file the audit named>` and the missing line ids, and send the repair batch it writes. If the saved copies of a line differ, give only the newest. If no copy exists, write the line as it stands in the Benchling entry into a file of your own in the run folder (`{ "lines": [{ "id": "<the id from moved>", "type": "text", "text": …, "at": … }] }`) and give that file as `--copies`; say in the report that it was rebuilt from Benchling. If the notebook itself no longer exists, the tool plans nothing: tell the user and ask. The audit's other findings (an id that appears twice, a document near the size limit) go into the report; change nothing for them without the user's yes.
- **Edits during a transfer.** A line the user changes in Daily while the transfer is running is moved with the wording the session read. If Daily's version changed between your read and your batch, re-read and use the new wording, in Benchling as well. (The pin makes the tool's batch fail in that case, so the old wording cannot be written over the new.)
- **Tidy `moved`.** Remove entries in `moved` older than 30 days whose ids are not in `blocks`, in the same batch as a move or in a pinned update of their own (the tool does this in every plan; an entry whose line is back in Daily is kept).
- Never write to `logs/todo`, to `config/tabs`, or to any other document in `logs` except `logs/daily` (the others belong to tabs the user added), and never change a line's `id`, `at` or wording. Meetings (`kind: "meeting"`) are left alone unless the user asks for one to be transferred. (The tool plans writes to `logs/daily` and to one notebook in `entries` only, and copies lines whole.)
- **Older notebooks.** Notebooks made before Daily existed may hold lines that were never transferred: a notebook with no `lastTransfer`, or lines with `at` later than `lastTransfer.at`. When the user asks to transfer, include those: write them to Benchling, leave them in their notebook, and set `lastTransfer = { at: <now, ISO>, benchlingUrl }` on that notebook. The audit lists these notebooks ("lines that may never have been transferred"), leaving out lines that `moved` shows came from Daily. It cannot tell a line moved from Daily more than 30 days ago from one typed straight into the notebook, so check the Benchling entry before writing a line there a second time. Setting `lastTransfer` is a pinned update of that one field, made with the data tool; the tool has no command for it.
